## The design decisions worth knowing

### TOTP is hand-written, not a dependency

`server/src/auth/mfa/totp.ts` implements RFC 4648 base32, RFC 4226 HOTP and RFC 6238 TOTP in about
a hundred lines of arithmetic. That is a deliberate choice for code sitting directly on the sign-in
route: every package added there is a package that can be taken over, and this one is small enough
to be verified by reading.

Correctness is not asserted against itself. `totp.spec.ts` checks it against the test vectors
**published in the RFCs** — all seven base32 vectors from RFC 4648 §10, all ten HOTP counters from
RFC 4226 Appendix D, and all six TOTP timestamps from RFC 6238 Appendix B. If those pass, an
authenticator app agrees with this server. Self-generated expectations would pass just as happily
while nobody could sign in.

The e2e suite deliberately contains a **second, independent** TOTP implementation rather than
importing the server's. Importing it would make the two agree by construction.

**SHA-1 is correct here.** RFC 6238 specifies HMAC-SHA1, every common authenticator implements it,
and most ignore the `algorithm` parameter entirely. SHA-1's collision weaknesses do not bear on
HMAC. Choosing SHA-256 would break scanning in common apps and buy nothing.

### Replay is refused — the part RFC 6238 leaves out

A TOTP code is valid for its whole 30-second step plus the window either side: roughly 90 seconds.
Without further work, a code seen over a shoulder, left in a screenshot, or captured by a phishing
proxy can be used **again** by somebody else inside that window.

`user_mfa_methods.last_step` records the step that was accepted, and anything at or below it is
refused. That is what makes a code genuinely single-use. It is proved twice: once against real rows,
and once end-to-end with two browsers racing the same code, where only the first gets in.

It also surfaced in development exactly as intended — three e2e tests failed with 422 because
confirming enrolment had already spent that step, and the challenge had to use the next one.

### A secret is never stored readably

`mfa-crypto.ts` seals TOTP secrets with AES-256-GCM under a key derived from `APP_KEY` with its own
domain separator.

It differs from the existing `meta-crypto.ts` in one deliberate way: **there is no plaintext
fallback.** `encryptToken` writes a `plain:` marker when `APP_KEY` is absent, which is a reasonable
trade for a Meta token — the alternative is a feature nobody can use. It is the wrong trade for a
second factor. A readable TOTP secret is a permanent bypass for anyone who can read a backup, a
replica or a support export, and it fails silently, because everything keeps working. Enrolment is
**refused** without a key, and the interface says why.

Recovery codes, one-time codes and trusted-device tokens are **hashed**, not encrypted — they are
only ever compared, never read back. SHA-256 keyed with `APP_KEY`, not bcrypt: the reasoning is the
opposite of the password case. Every one is generated from `randomBytes` with 80+ bits of entropy
and none is chosen by a person, so there is no dictionary to run and no reuse to exploit — the work
factor buys nothing while costing real time on a login route.

### The half-finished sign-in reaches nothing

When a password is correct but a factor is outstanding, the session carries `mfaPendingUserId` —
**a different key from `userId`**. `AuthGuard` reads `userId` and only `userId`, so a pending session
reaches no endpoint in the application. Half-authenticated is not a weaker kind of authenticated
here; it is simply not authenticated, and that is true by construction rather than by every guard
remembering to check a flag.

The pending state expires in 10 minutes, enforced in code rather than by the cookie, and the session
identifier is regenerated at **both** steps — so Phase 2's fixation fix has no gap in the middle of a
two-step sign-in.

The challenge response carries **no user payload**: not a name, not a role, not a permission map. At
that point a password has been proved and nothing else, and the payload is the thing being protected.

### Nothing tells an unauthenticated caller about an account

`POST /api/login/mfa/send` answers *"If that method is set up, a code is on its way"* whether or not
anything was sent, and whether or not delivery succeeded. Whether a channel is configured, whether an
address is reachable, and whether the message went out are all facts about an account — and the
caller has proved a password, which is exactly what a thief also has. Failures are logged for whoever
has to explain them.

### Trusted devices are an honest trade-off

The cookie lets a browser skip the challenge, so anyone holding it has the second factor for as long
as it lasts. What keeps that acceptable: 256 bits of randomness, stored hashed; `HttpOnly`; a 30-day
expiry; bound to **one** user; revoked wholesale when the password changes or the factors change;
and listed on the security screen with its last use so an unfamiliar one can be revoked.

It is never a default — trusting must be explicitly chosen, and there is a test that proves an
ordinary sign-in does not grant it.

### The policy cannot lock out a brokerage by accident

`mfa_policies` is per role, per brokerage, and **empty by default** — installing this feature changes
nobody's sign-in. Switching a requirement on gives a grace period (7 days by default) measured from
the *later* of the policy change and the account's creation, so somebody hired afterwards gets their
own full window rather than a deadline that already expired.

## The authorization hole found while building it

`MfaAdminController` was first written with `@Screen('users', 'edit')` on its methods and only
`@UseGuards(AuthGuard)` on the class.

**`ScreenGuard` is not registered globally in this application.** A controller that omits it turns
every `@Screen` decorator into a comment. As first written, any signed-in agent could have cleared an
administrator's second factor and rewritten the brokerage's policy.

Caught by checking `app.module.ts` rather than assuming, fixed by adding the guard, and
sensitivity-checked: with `ScreenGuard` removed, `an ordinary agent CANNOT reset somebody else's
two-factor` and `an ordinary agent cannot rewrite the brokerage policy` both go red.

## The module graph problem, and why `ModuleRef`

The obvious wiring — `AuthModule` imports `EmailModule` and `SmsModule` so codes can be sent — does
not work. Both already import `AuthModule` for the auth guards, so importing them back closes a
cycle. `forwardRef` on both ends moves the failure rather than fixing it: `EmailModule` also imports
`SettingsModule`, which imports `AuthModule` in turn, and the cycle reappears one level out. The
application refused to boot at each step; this was measured, not predicted.

`OtpDeliveryService` resolves `MailerService` and `TwilioService` through `ModuleRef` with
`strict: false` instead. The cost is that a missing provider becomes a runtime rather than a boot
failure, so both log loudly and report the code as undelivered rather than throwing into the sign-in
path — and `e2e/tests/mfa.spec.ts` asserts `GET /api/mfa` really does report `email` among its
available channels against a running application.

The `forwardRef` edits to `EmailModule` and `SmsModule` were **reverted**; no module outside
`auth/` was changed.

## Database

Migration `20260806120000_mfa` — five tables, **additive only**, safe to apply while serving:

`user_mfa_methods`, `mfa_recovery_codes`, `mfa_trusted_devices`, `mfa_challenges`, `mfa_policies`.

All five are `ON DELETE CASCADE` from `users` (or `company_settings` for the policy). An orphaned
trusted-device row would leave a working credential behind for an account that no longer exists.

Classified in `src/core/tenancy.spec.ts`, which fails if a new table arrives unclassified: the four
per-user tables are DERIVED via `users` with a denormalised `company_id`, exactly like
`user_permissions`; `mfa_policies` is ROOT, owned by the brokerage directly.

**The migration was hand-written.** `prisma migrate diff` against the schema also emitted a long tail
of unrelated drift — dropping `campaigns_scheduled_for_idx` and `transactions_agent_user_id_idx`,
renaming a dozen indexes, and re-creating foreign keys on calendar, `crm_settings` and
`push_subscriptions` — because earlier migrations were hand-written and the recorded history no
longer matches what Prisma would generate. **That drift is a real, pre-existing issue worth
addressing on its own**, but dropping working indexes as a side effect of adding two-factor would
have been a genuine regression, so only the MFA objects are in this migration.

## Two guard-rail tests that had to be updated

Both failed, and both were right to:

- `src/core/tenant-context.spec.ts` requires every use of `runAsSystem` to carry a written
  justification. The four MFA services use it because they are read **during** sign-in, before a
  session exists to name a tenant — the same reason `auth.service.ts` is on that list. Every query is
  bounded by `user_id` instead, and the id comes from the pending session the server itself
  established, never from anything the caller supplied. Justifications added.
- `src/config/rate-limits.spec.ts` counts the endpoints carrying the strict `AUTH_LIMIT`. It moved
  from 3 to 5 because the challenge and its resend now carry it too. Updated, with a second
  assertion added covering the management endpoints.

## Frontend

- `client/src/pages/MfaChallenge.tsx` — the second sign-in step. `autocomplete="one-time-code"`, so
  iOS and Android offer the code from a text message. Method switching, resend, recovery-code entry,
  and an explicit "do not ask again on this device".
- `client/src/desk/TwoFactorCard.tsx` — on Account Settings. Enrolment, recovery codes shown once
  with a plain warning, method removal behind the password, and the trusted-device list.
- `client/src/lib/mfaApi.ts` — the API layer.
- `AuthContext.login` now resolves to **either** a signed-in user or an outstanding challenge, and
  deliberately does not call `setUser` on a challenge. Setting a user there would make the whole
  application behave as though sign-in had succeeded while the server still refuses every request.

**One dependency added: `qrcode` (client only).** The QR is rendered **locally in the browser** from
the `otpauth://` URI. A third-party QR service would mean posting a second-factor secret to a
stranger, which is not acceptable at any convenience. The secret is already in the DOM for manual
entry, so this adds no new category of exposure. Manual entry is always offered beside the QR —
cameras fail, and an enrolment that only works by scanning is one a desktop user cannot complete.

## Known limitations, stated plainly

- **Recovery codes cannot be re-shown.** By design — they are hashed. Someone who loses them must
  regenerate, or ask an administrator to reset.
- **`grace_days: 0` is not precisely instantaneous.** `updated_at` is `TIMESTAMP(0)` and Postgres
  *rounds* to the nearest second, so a policy can sit up to half a second in the future. Irrelevant
  to a deadline measured in days; documented because a test had to account for it.
- **The policy is advisory in the API.** `obligation` is returned on sign-in and on the settings
  screen, and the interface acts on it, but no server-side guard yet blocks an overdue account from
  using the rest of the application. That is a deliberate stopping point: a global enforcement guard
  is the one part of this feature that could lock out a brokerage if it were wrong, and it deserves
  its own change with its own tests rather than riding along here.
- **The account lockout remains in-process.** Unchanged from before; see
  `account-lockout.service.ts`. It bounds password guessing, not code guessing — the per-code attempt
  ceiling and `AUTH_LIMIT` do that.
- **SMS depends on Twilio being configured.** Where it is not, the channel is not offered for
  enrolment at all, so nobody can lock an account behind a factor that cannot be delivered.

## Operational note

`APP_KEY` **must be set** for authenticator enrolment to work. Where it is absent the option is
refused and the settings screen explains why, rather than storing a secret that would be readable.
Email and SMS codes still work without it.

The credentials flagged in earlier phases still require rotation; nothing in this phase changes that.
